# Garden × Playground 生图服务维护说明

更新：2026-11-09。本文描述现行实现；旧任务书中的强制统一动态路由和复杂权限要求已取消，旧阶段流水由 Git 历史追溯。

## 架构和数据归属

Garden AI Service 是唯一生图执行方，接口按业务分开：

- A：Garden 庭院效果图，保留 Scheme/Revision、素材组织、归档及既有动态路由。
- B：Playground 通用生图，提交时锁定供应商配置，不套庭院 Prompt，不强制合并 A/B 的选商策略。
- 两者共享 Garden 供应商配置、Key、Worker、并发控制、私有媒体与后台调用记录。Playground 浏览器和图库服务不执行第三方生图调用。
- 生图权限使用 Garden 现有账号与 Session；普通通用任务只允许提交人读取，后台沿用原 PlatformAdmin。不增加部门、角色、审批或计费模块。

**Playground 公司图库仍用原数据库和媒体目录，Garden 庭院数据仍在自己的库表/媒体卷。** 公司图库历史没有导入庭院项目或统一任务表；新 Playground 请求作为来源 playground 的 GenericImageJob 执行，结果再按原前端流程归档到公司图库。

浏览器还保留 IndexedDB 工作区历史、原始输出和本地参数；同站点同浏览器未清数据时继续读取。不要通过删 IndexedDB、图库数据库或媒体目录处理升级问题。

## 接口和恢复约定

- `GET /api/image-capabilities`：服务能力；前端按实际上限校验。目前通用任务最多4张输出、3张参考图，供应商声明可能更低。
- `POST /api/image-jobs`：source_app=playground，提交prompt、params、client_request_id及可选有序参考图。
- `GET /api/image-jobs/{job_id}`、`GET /api/image-jobs/{job_id}/results/{index}`：查原任务和取图；`POST .../cancel`取消。
- 浏览器先持久化gardenRequestId，未知提交结果时复用原幂等键；得到job_id后只查询原任务。相同键但内容变化返回409，不自动换键重发，避免重复计费。
- HTTP页面使用 `src/lib/uuid.ts` 的createUuid（crypto.getRandomValues实现），不要直接调用受安全上下文限制的crypto.randomUUID。旧ID和任务恢复数据保持不变。
- 已成功iteration不重发；522/523/524等结果未知时不自动重复提交。后台只展示已有调用事实，不推测费用。

Garden后台“生图记录”支持全部/Garden/Playground来源、时间、用户和合并分页；管理员可预览两类任务及通用多图，原庭院结果URL保持兼容。普通任务读取与后台管理权限不同，不开放公开结果URL。

## 验证和发布

使用npm和Node22，勿复用其他项目依赖。常用验证：

```bash
npm run build
npm test
npm run test:mock
python3 -m unittest discover -s deploy -p test_garden_gateway.py
```

`node scripts/verify-http-generation.mjs http://<非localhost地址>:<端口>` 会在真实HTTP页面点击生成，并在浏览器拦截所有相关API验证UUID、结果保存、刷新防重放；**不调用真实供应商**。需要已安装Garden前端的Playwright依赖，可用GARDEN_ROOT指定Garden仓库位置。

`scripts/verify-garden-integration.mjs`是隔离真实联调工具，显式传`--real --config <本机配置文件> --reference <参考图>`才运行，会提交真实付费任务；`--resume <该脚本隔离目录>`只续查两条成功任务，不补提。不要为重新看日志重跑付费任务；临时目录中可能有配置密钥，不能提交或打包。

HTTP修复后：71个文件942项单测、构建、非安全HTTP按钮提交/结果持久化/刷新回归通过。Garden集成已跑相关后端193项、前端3077项（14 skip）、构建和后台浏览器2项；这不是完整Main/Touch/GitHub CI通过声明，远端门禁状态看PR。

先发布可服务通用API的Garden，再更新Playground。只更新Playground程序/静态文件和必要网关配置，不覆盖data。共享数据库迁移需Garden联合维护流程，不能绕过AI-only兼容检查。Garden生产当前为g1_generic_jobs；集成dev含上游场地迁移与无数据变更的g1_b1_merge汇合，不能直接当作同schema的AI-only更新。

升级前冷备；回退优先保留新任务表和数据。旧Core镜像若不认识新增Alembic修订，不能直接让其默认启动命令再次执行旧alembic upgrade head；先按Garden运行手册核对回退启动和schema。不要用删除generic表当无损回滚。
